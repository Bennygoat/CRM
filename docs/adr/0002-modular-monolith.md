# ADR 0002：採用模組化單體

| 項目 | 內容 |
|---|---|
| 狀態 | 已接受；第 8 節的待決定問題在搬移 package 前定案 |
| 日期 | 2026-11-07 |
| 工單 | CRM-57 |
| 相關 ADR | [ADR 0001：資料模型重整](0001-data-model.md) |

本文件的決定來自 CRM-57 留言「架構決定」，由使用者確認。標示「建議」的內容是對照程式後補上的，還沒定案，都列在第 8 節。

## 1. 背景

使用者希望分階段上線：先做 CRM，日後再擴充會計等功能，而且使用者看起來仍是同一套系統。

後端目前依技術分層，`controller`、`service`、`repository` 各放一起，看不出模組邊界，模組之間也互相直接使用對方的資料：

- `InventoryService` 直接用 `SalesOrderRepository`、`SalesShipmentRepository`，出貨邏輯放在庫存這一側。
- `DashboardService` 同時查銷貨和庫存的 Repository。
- 銷貨明細的 Entity 直接關聯 `Product`、`Warehouse`。

如果不先定邊界，之後加功能只會讓這些依賴越來越多，日後想分開也分不開。

## 2. 決定：模組化單體

模組化單體（Modular Monolith）是把程式切成邊界清楚的模組，但部署時仍是一個服務。單體指只有一個可部署的程式；模組化指程式內部有明確的分區和規則。

**原因**

- 目前只有一個人維護。微服務（Microservices，每個模組獨立部署成一個服務）要多管部署、監控和服務間通訊，現階段沒有對應的收益。
- 下單時預留庫存要和建立訂單在同一個交易內完成。留在同一個服務，一個資料庫交易就能保證一致；拆開就要處理分散式交易。
- 先把邊界做好，日後要拆成獨立服務時，改動範圍會小很多。

**取捨**

| 面向 | 好處 | 代價 |
|---|---|---|
| 部署 | 只有一個服務和一個資料庫 | 一個模組出問題可能影響全部，也無法個別擴充 |
| 交易 | 跨模組的一致性容易保證 | 模組會傾向共用交易，日後拆分時要重新設計 |
| 邊界 | 不需要網路呼叫 | 邊界靠規則維持，同一個專案裡違規也編譯得過 |

**放棄的做法**

| 做法 | 放棄的原因 |
|---|---|
| 一開始就拆兩個 server | 現在沒有獨立擴充或分團隊的需求，卻要先付部署和跨服務交易的成本 |
| 加 Go 服務 | 多一種語言和部署方式，目前沒有 Java 解決不了的問題 |
| 靠 CORS 串接多個服務 | CORS（Cross-Origin Resource Sharing，瀏覽器允許網頁呼叫不同網域的規則）只解決瀏覽器能不能呼叫，使用者看到的仍是多個網址，登入狀態和設定也要跨網域處理。需要分開時改用反向代理，見第 7 節 |
| 用單一 0/1 參數開關 | 把兩件不同的事混在一起：模組裝不裝，以及稅率、運費這類可調數值。而且只有一個開關，無法表達各模組的狀態 |

CRM-57 背景另外列了「外接 jar」，架構決定沒有提到，這裡不算放棄，見 Q5。

## 3. 模組規劃

| 模組 | 用途 |
|---|---|
| `crm-app` | 啟動程式，把各模組組裝起來 |
| `crm-common` | 各模組共用的基礎程式 |
| `crm-sales` | 銷售相關功能 |
| `crm-inventory` | 庫存相關功能 |
| `crm-accounting` | 會計，之後才新增 |

每個模組擁有哪些資料表還沒定案，建議見 Q1。

## 4. 三條規則

### 規則一：模組不能直接查別人的資料表

要透過對方的公開介面或事件。

- **公開介面**：模組對外提供的 Service 介面，例如銷售呼叫庫存的「預留庫存」。需要立刻知道結果時用這個。
- **事件**：模組發出「發生了什麼事」，其他模組自己決定要不要處理，發送方不用認識接收方。專案已有這種用法，例如 `SalesOrderShippedEvent`。

這條規則的目的，是讓一個模組改資料表時，只影響自己。

### 規則二：開關分兩層

| 層級 | 控制什麼 | 放哪裡 | 什麼時候生效 |
|---|---|---|---|
| 模組開關 | 模組裝不裝 | 啟動設定 | 重新啟動 |
| 可調參數 | 稅率、運費等數值 | `system_params` 資料表 | 程式下次讀取時 |

模組裝不裝決定了程式要載入哪些 Bean 和路由，不適合在執行中切換，所以放啟動設定。稅率、運費是營運會調整的數值，放資料庫才不用重新部署。

`system_params` 要在 V1 建立，因為第一批的運費和稅率就會用到，見 [ADR 0001](0001-data-model.md) 的 Q15、Q16。

### 規則三：前後端都要依開關生效

前端依開關隱藏選單，後端也要擋 API，不能只靠前端。隱藏選單只是不顯示入口，任何人仍可直接呼叫 API，所以真正的限制要在後端。

建議後端用啟動設定決定是否載入模組的 Controller，模組沒裝時路由就不存在；前端從後端取得已啟用的模組清單，不在前端另存一份設定。

## 5. 時程

| 階段 | 內容 | 時機 |
|---|---|---|
| 1 | 依模組整理 package，依賴方向用規則約束 | 隨 CRM-35 逐模組遷移 |
| 2 | 拆成 Maven 模組 | 第二個模組真的要獨立時 |
| 3 | 拆成獨立服務 | 符合第 7 節的條件時 |

Maven 模組是把專案分成多個子專案，各自宣告依賴。這樣的好處是違反依賴方向時會編譯失敗；代價是建置設定變複雜，所以等有需要才拆。在這之前，第 3 節的模組名稱對應到 package，不是 Maven 子專案。

這個決定不拖慢 Flyway V1：V1 只處理資料表，package 搬移另外進行。

## 6. 對既有工作的影響

- **CRM-35**：逐模組遷移時，同時把程式搬到模組的 package，不必分兩次。
- **CRM-45、CRM-51**：運費和稅率的可調參數放 `system_params`。
- **CRM-42**：B2C 改接 `SalesOrder` 時，新程式就要遵守規則一，庫存操作走 `InventoryService` 的方法。
- **`InventoryService.shipSalesOrder`**：這段出貨流程跨越銷售和庫存，遷移時要決定歸屬，見 Q2。

## 7. 日後拆成獨立服務的條件

符合任一條件才考慮拆：

- 模組需要獨立擴充。
- 模組交給另一個團隊維護。

屆時用反向代理（Reverse Proxy，對外只有一個入口，再依路徑把請求轉給後面不同的服務）維持同一個網址，不靠 CORS 串接。使用者仍然只看到一套系統。

## 8. 待決定問題

CRM-57 沒有決定這些細節，建議只是起點。

**Q1：每個模組擁有哪些資料表？**
建議：

| 模組 | 資料表 |
|---|---|
| `crm-common` | 員工、權限、操作紀錄、`system_params` |
| `crm-sales` | 客戶、聯絡人、商機、合約、活動、銷貨、出貨、退貨、購物車、優惠券、VIP、客服 |
| `crm-inventory` | 商品、分類、單位、供應商、倉庫、採購、庫存 |

`crm-sales` 放了 CRM 和銷售，範圍最大。如果客戶和商機要獨立上線，可能要再分出一個模組。`crm-accounting` 的範圍見 Q4。

**Q2：出貨單屬於哪個模組？**
建議屬於 `crm-sales`，由銷售呼叫庫存的公開介面扣庫存，依賴方向維持銷售到庫存的單向。

**Q3：規則一怎麼處理跨模組的外鍵和 JPA 關聯？**
ADR 0001 的資料模型有跨模組外鍵，例如 `sales_order_details.product_id`，Entity 也用 `@ManyToOne` 直接關聯。嚴格遵守規則一的話，這些關聯要改成只存 ID。

建議：

- 資料庫外鍵保留，單體階段它們是保護資料一致的最後防線，V1 不受影響。
- Java 的跨模組 `@ManyToOne` 先保留，避免和 V1 那批改動互相牽動；新程式不透過它們讀別模組的資料，遷移到該模組時再改成只存 ID。
- `crm-common` 的 `users` 被所有模組的稽核欄位參照，視為例外。
- `DashboardService` 這類跨模組統計要定案：改走各模組的查詢介面，或另外開放唯讀的報表查詢。

**Q4：`crm-accounting` 的範圍？**
[ADR 0001](0001-data-model.md) 把總帳列為不做，應收應付（CRM-55）則是第二批。建議 `crm-accounting` 只放應收應付與沖帳，總帳仍不在範圍；也要定案 CRM-55 上線時就建這個模組，還是先放在 `crm-sales`。

**Q5：其他還沒定的細節？**

- 模組開關的設定名稱，以及前端取得清單的 API。
- 哪些模組可以關閉。`crm-sales` 下單要預留庫存，建議先規定 `crm-inventory` 不可單獨關閉，否則要另外處理沒有庫存模組時的流程。
- 根 package 的名稱，要和 CRM-24 的更名一起看。
- CRM-57 背景列的外接 jar，也就是執行時才載入外部模組，是否正式放棄。建議放棄，Maven 模組已能滿足目前的規劃。

## 9. 結果

**好處**

- 可以先上線 CRM，日後加模組，使用者仍看到同一套系統。
- 模組邊界清楚後，改一個模組的影響範圍變小。
- 部署維持單純，一個人維護得來。

**代價**

- package 階段的邊界只靠規則和 Code Review 維持，編譯不會擋。
- 現有的跨模組依賴要逐步清理，遷移期間新舊寫法會並存。
- 多一層公開介面，簡單的查詢也要多寫一點程式。
